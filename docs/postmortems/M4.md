## 关键技术决策（固化）

### D1：同步 fetch 桥而非 Promise
- boa 0.20 的 Promise 需要 JobQueue + 异步 runtime 嵌套，复杂度爆炸
- `__fetchSetBody(url)` 直接同步阻塞 → JS 写起来像同步代码 → 爬虫场景天然适用
- 实现：`std::thread::spawn` + 新 `current_thread` tokio runtime，避开 outer runtime 嵌套 panic
- 代价：JS 不能并发请求；SPA 真实场景中 fetch 顺序通常是串行的，影响有限

### D2：相对 URL resolve 用 RFC 3986
- 复用 `url::Url::join()` 实现，零手写
- 例子：base=`/spa` + rel=`api/comments` → `/api/comments`（last-segment-replaced）
- 浏览器标准行为；爬虫依赖这个语义

### D3：layout 抑制 `<script>/<style>` 内容
- M2 时漏了：浏览器不渲染 `<script>`/`<style>` 内文本，我们的 layout 却把 JS 源码当 text 渲染了
- M4.1 顺手修了——`is_non_rendered_tag()` 黑名单
- 教训：layout 引擎需要尊重"head/script/style/template/noscript 不渲染"约定

### D4：write-only bridge + base URL 在调用线程 resolve
- `BASE_URL` 是 thread-local；`fetch_sync` 跑在新线程里读不到
- 解：`fetch_set_body` 在调用线程先 `resolve_url()` 得到绝对 URL，再传给 `fetch_sync`
- 模式：跨线程边界前先做"序列化"，避免 thread-local 跨线程

## 踩坑记录

### 1. boa 0.20 的 `from_fn` 闭包不能携带非 `Trace` 捕获
- 延续 M3.2 的方案：thread-local slot + `NativeFunction::from_fn_ptr`
- 教训：嵌入 JS 引擎时，捕获策略要早决定（Rc<RefCell<T>> 或 thread-local）

### 2. tokio 嵌套：从 boa 内部 `block_on` 触发 panic
- **现象：** 直接在 boa native fn 里 `tokio::runtime::Handle::current().block_on(...)` 会 panic "Cannot block the current thread"
- **解决：** `std::thread::spawn(move || { new_runtime.block_on(...) })` + `handle.join()`
- 教训：嵌入异步 VM 时，"同步桥到异步"的标准解法是 detached worker thread

### 3. wiremock path 匹配 + RFC 3986 resolve 的预期错位
- **现象：** 测试期望 mock 命中 `/spa/api/comments`，实际 wiremock 收到 `/api/comments`
- **根因：** URL resolve 按 RFC 3986 规则替换 last segment，base `/spa` 不是目录
- **解决：** 改测试期望为 RFC 行为；用 `resolve_url_with_base_joins_relative` 单测覆盖所有边界
- 教训：URL resolve 语义容易踩坑，必须有单测覆盖 `/abs`、`rel`、`../rel`、`abs-url` 四种

### 4. `<script>` 注释当文本渲染
- **现象：** M3.4 用 spa-blog.html 时，`render-file` 输出包含 `// Simulate a tiny SPA bootstrap...`
- **根因：** M2 layout 把 `<script>` 子树当 inline text 处理
- **解决：** M4.1 加 `is_non_rendered_tag` 黑名单
- 教训：浏览器"不渲染某些标签"是个长尾清单，layout 引擎必须有黑名单

### 5. CLI 多次 edit 文件导致 mock 顺序错乱
- **现象：** 反复 edit 测试文件时，前一次 edit 删了 mock 块，新 edit 在错误位置追加
- **解决：** `git checkout <commit> -- <file>` 回滚 + `cat >>` 干净 append
- 教训：测试文件复杂度上去后，edit 不可靠，应该写到独立 commit 再合并

## 经验沉淀

### 技术经验
- 嵌入式 JS 引擎的"同步桥到异步"标准 pattern：worker thread + new runtime + `join()`
- thread-local 跨线程边界（如 detached worker）必须先序列化关键状态
- URL resolve 语义需要专门测试，依赖直觉容易踩坑
- 浏览器不渲染的标签清单：script/style/template/noscript/注释/doctype

### 工程经验
- boa 0.20 的 `from_fn_ptr` + 显式 `as NativeFn` 是最稳的 native fn 注册方式
- "write-only bridge → 加 read-only → 加 fetch → 加 resolve" 增量演进，每步可独立验证
- SPA fixture 用 wiremock（不用真 React/Vue 应用）让管线可重复测试，不依赖外网
- `assert_cmd` + `wiremock` + `predicate` 三件套对 CLI e2e 测试非常合适

### 流程经验
- M4 把 SPA 渲染切成 5 步，每步独立提交，每步有 e2e 验证
- 当一个测试卡住时，先 `git checkout` 回滚到上个干净状态再重写，比反复 edit 快
- "先 write-only 跑通再扩展" 比"一上来完整 API"省 5x 时间
