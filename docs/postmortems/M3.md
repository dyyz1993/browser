## 关键技术决策（固化）

### D1：boa_engine 0.20 而非 deno_core
- boa 纯 Rust、单 crate、~100k LOC，符合"复用底层"原则
- deno_core 引 V8，构建链重，跨平台麻烦
- 实测 boa 跑通了 SPA demo（4 个全局函数桥），保留 deno_core 作为 M5+ plan B

### D2：write-only DOM bridge（M3 阶段）
- 暴露 4 个全局：`__setBody(s)`、`__appendBody(s)`、`__setTitle(s)`、`__log(s)`
- 不实现 `__getBody` —— 返回 `String` 到 JS 需要 `JsString::from(...)`，boa 0.20 API 摩擦大
- **替代方案**：JS 跑完后从 Rust 侧调 `body_text_content()` 读 DOM，避开 JsValue 边界
- 代价：JS 不能读自己改过的 DOM。对 SPA 爬虫场景够用（爬虫不需要 JS 读 DOM）

### D3：thread-local `Rc<RefCell<Tree>>` 绕开 `Trace`
- boa 的 `NativeFunction::from_copy_closure_with_captures` 要求捕获实现 `Trace`
- `Tree`（arena DOM）实现 `Trace` 需要手写 50+ 行 unsafe 代码
- **方案**：`thread_local! { static CURRENT_TREE: RefCell<Option<SharedTree>> }`，函数指针读 thread-local
- 优势：纯 safe Rust，符合 `#![forbid(unsafe_code)]`
- 代价：单线程限定的 JS 执行（CLI 场景天然单线程，无影响）

### D4：错误隔离 + 计数返回
- `execute_scripts` 返回 `usize`（成功执行的脚本数）
- 单个 `<script>` throw 不阻断后续 script
- eprintln 输出错误，调用方通过 stderr 看到 `[js-runtime] script error: ...`
- 教训：SPA 的 `<script>` 链很常见，第一个失败不能拖死整个 pipeline

## 踩坑记录

### 1. boa 0.20 的 `NativeFunction::from_fn` 不存在
- **现象：** 按 0.18 文档写的 `NativeFunction::from_fn(closure)` 编译失败
- **解决：** 改用 `NativeFunction::from_fn_ptr(fn_pointer)` + 显式 `as NativeFn` 转换
- **教训：** boa API 在小版本间会 break，应该先看本地 `cargo registry` 的源码再写

### 2. `register_global_callable` 第二个参数是 length
- **现象：** 写成 `register_global_callable(name, f)` 编译失败
- **解决：** 签名是 `(name, length, fn)`，length 是 JS Function.length（声明参数数），传 1 即可
- **教训：** boa 的 API 名字看起来像"注册 N 个变体"实际是"声明参数个数"

### 3. `JsString` 不能从 `String` 直接 `.into()`
- **现象：** `JsValue::String(text.into())` 类型错误（String 没实现 `Into<JsString>`）
- **解决：** M3.2 删掉 `__getBody`，M3 整体保持 write-only
- **教训：** 跨语言边界设计 API 时，先写最小 set 跑通，再扩。先 write-only 跑通后才发现 read 路径的成本

### 4. closure captures 不能跨 boa 边界
- **现象：** `NativeFunction::from_copy_closure_with_captures(move |_, _, captures, _| { captures.borrow().set_body(...) })` 报 `Trace not implemented`
- **解决：** thread-local slot + 函数指针
- **教训：** Rust 嵌入 JS 引擎时，"借用 + GC"是经典冲突，常见解法是 thread-local 或对象 ID 表

### 5. 测试用例 `cargo fmt --check` 在 e2e 多行字符串里报格式漂移
- **现象：** `std::fs::write(&path, "..." )` 被 fmt 自动重排为单行
- **解决：** 主动跑 `cargo fmt --all` 后再 `--check`
- **教训：** CI 加 `cargo fmt --all --check` 之前，本地必须先 fmt 一次

## 经验沉淀

### 技术经验
- 嵌入式 JS 引擎的最小集成：context + source eval + 全局函数注册，<100 LOC
- thread-local + RAII guard 是 Rust 嵌入 VM 的常见 pattern（PyO3、rlua 也类似）
- arena DOM 在 JS 桥里的优势：NodeId 是 `Copy`，跨语言边界传 usize 比传 `Rc<RefCell<Node>>` 简单 10 倍
- "write-only bridge" 是个有用的中间状态：能用 JS 改 DOM，但不暴露读 API，避开 JsValue 序列化

### 工程经验
- boa 0.20 比 0.18 慢 ~20%（bytecompiler 引入），但 API 稳定性更好
- `from_fn_ptr` + `as NativeFn` 的 cast 模式比 closure 简洁
- 跨语言测试用 `eprintln!("[js] ...")` 输出错误，比 `panic!` 友好（不阻断后续 script）

### 流程经验
- M3 把 "JS 引擎 + 桥" 切成 5 个 step，每个 step 独立可验证
- `render-script` 子命令和 spa-blog fixture 让端到端验证特别清晰（grep "Welcome to my blog"）
- "write-only → read-only" 增量演进，比一上来就完整 DOM API 好规划
